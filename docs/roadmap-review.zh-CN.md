## 2. Week 1 已完成

按你的 Week 1 定义（阅读 Work2Skill、建立录制数据格式、一个可运行的 Web 操作样例、明确复现/原创边界）已经做完并跑通：

- 可运行样例：`run_sample.py` 会起本地 Web 应用、录制一条完整演示、产出 23 个动作 / 24 张证据帧 / 64 条原始事件 / video.mp4；

一个需要你知道的取舍：**演示目前是脚本驱动的，不是真人操作。** 录制、稳态判定、取帧、动作分组、打包这五层是真人会话会走的同一套代码，只有输入来源不同。格式层因此是真实的，但"人类演示"这个前提在 Week 1 还没有真正验证过。这是有意为之的 Week-1 范围，不是遗忘。

## 3. 三处需要调整

### 3.1 宏回放基线应该提到最前面，它是你唯一的真原创点

你的 Week 3 写"对比原始 Agent、固定宏回放、归纳后的 Skill"。**这个宏回放基线论文里没有。**

论文的对照组是 No Skill、ShowUI-Aloha、Demo2Tutorial —— 三个全是*文本指导*方法。没有一个在测那个最便宜、最显然的替代方案：把录下来的动作序列原样重放。

这不是小疏忽，它直接决定你的项目有没有立足点：

- 如果固定宏在演示过的任务上得分接近归纳出的 skill，那归纳这一步就不值它的成本；
- 如果宏在扰动页面上崩掉而 skill 还活着，**那才是 induction 存在的理由**，而且是一个论文没有提供的证据。

所以宏回放不只是"对照组之一"，它应该是你实验的中心。建议挪到 Week 2 一起做（它实现起来比归纳简单得多），而不是等到 Week 3。

### 3.2 Week 2 被低估了

"动作定位、步骤依赖和完成条件"——这三件事里，第三件（完成条件）才是真正的工作量，而且前两件有现成答案。

- **动作定位**：Web 上退化成了简单问题。DOM 直接可读，`data-testid` / role / accessible name 一把拿全，比论文在 Linux 上靠 AT-SPI 点查询 + 邻近事件回填 + 2.5 秒最近邻兜底要干净得多。我们已经把它做完了（`target` 字段）。
- **步骤依赖**：从 trace 里建依赖图是有成熟做法的部分。
- **完成条件**：这才是没有现成答案的地方。论文的处理方式是让 agent 在授权策略约束下自己写"可观察的完成检查"，而且明确说了 `finalize extraction` **只校验输出结构，不校验 skill 是否正确或任务是否成功**。也就是说：完成条件对不对，论文自己也没做自动验证。

你的评测要落地，绕不开给每个任务写一个状态断言。这恰好是 `bench/site` 的 `/api/state` 存在的理由——任务成败是服务器状态的纯函数，不需要人看截图。建议 Week 2 就把每个任务的断言写完，别拖到 Week 3。

### 3.3 Week 4 才开源，太晚

"发布 README → 出 Benchmark → 出技术报告 → 出视频"排在第 4 周，意味着前三周没有任何外部反馈，而且如果第 3 周的实验结果是负面的（很可能——见下），第 4 周的"发布"就没有东西可发。

建议 Day 1 就 public，每完成一块推一次。理由不只是"早发布早反馈"：这个项目的价值主张建立在"论文结果能否在 Web 上复现"之上，而这件事有真实的不确定性。让它在有人看的情况下失败，比无人在场时失败好得多。

## 4. 复现 vs 原创：目前的划分

**复现**（对齐论文）：证据 schema（Appendix B）、rubric 隔离（task.json 不含评分字段，代码里强制）、采集策略（前帧 1.5 秒复用、稳态后取帧、滚动完成才记一次、`result_unsettled` 区分）、探索工具的接口面（Appendix C）。

**原创**：Web 替代桌面；宏回放基线；成本作为一等结果。

**不复现**：论文的桌面采集栈、WorkDemo-350、以及它的两个 benchmark 任务集。WorkDemo-350 需要 macOS 录制器和数小时人工演示；任务集依赖 MyPCBench 和 OSWorld 环境。官方仓库目前只发布了录制器、归纳示例和任务定义，评估集成仍标注为 pending。

这个切法是有意的：论文的采集栈（macOS ScreenCaptureKit + CoreGraphics 事件捕获 + Linux 客体经 SSH 隧道走 AT-SPI）是它最不可复现的部分，而它要研究的科学问题——人类程序性知识能否被归纳成可复用的参数化 skill——不依赖于跑在哪一种采集栈上。

## 5. 一个需要提前知道的坏消息：成本论据不成立

如果你的验证目标是"skill 比原始 Agent 更省成本"，论文自己的数据不支持这个说法。Table 2（GPT-5.5 / MyPCBench，64 任务）：

| | Score | SR | 执行步数 | 归纳 token |
|---|---|---|---|---|
| No Skill | 74.73 | 23.44% | 40.89 | — |
| ShowUI-Aloha | 77.48 | 37.50% | 41.33 | 170.65k |
| Demo2Tutorial | 75.25 | 37.50% | 46.13 | 177.32k |
| Work2Skill | 85.27 | 48.44% | 47.38 | 334.52k |

归纳 token 是基线的约 2 倍，执行步数比 No Skill 还多。论文自己也承认："Skill-induction token usage is also not consistently lower"，以及"Work2Skill uses fewer execution steps than No Skill for Opus-4.8 and both Qwen models, but more for GPT-5.5"。

另外注意**增益幅度**：对更强的那个基线，MyPCBench 上只领先 3.95–7.79 分，OSWorld 上只有 1.65–6.96 分。OSWorld 286 任务上 +1.65 分基本落在噪声区间里。

对你的 Week 3 的含义：成本要如实统计并如实报告，别把它写成优势。真正站得住的论点是**"在页面变化后 skill 仍然有效而固定宏失效"**——那是能力差异，不是效率差异，而且是你相对论文的新增证据。

## 6. 关于论文本身的两个方法论隐患

值得在你的评测里主动堵住：

1. **归纳期的信息泄漏。** 论文用的是同一条演示既做归纳又做评测。如果你的 skill 只在演示过的那个任务上评测，"泛化"就没有被验证。你的 Week 3 已经写了"未见任务和变化后的页面"，方向是对的——建议再加一条硬约束：归纳期可见的证据目录里绝不能出现评测任务的任何痕迹，`task.json` 无评分字段只是个开始。
2. **无人验证的完成条件。** 如上，`finalize extraction` 不校验 skill 正确性。论文里 skill 是否写对，唯一检验就是下游执行得分。这意味着"skill 质量"和"执行模型能力"在论文的实验里是混在一起的。
